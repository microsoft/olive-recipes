# llama.cpp 与 INT2 QMoE：实现差异和性能实验讨论

本文讨论本 recipe 的 ONNX Runtime（ORT）INT2 QMoE 与 llama.cpp CUDA 低比特计算的区别，以及借鉴其整数点积思路后的实验结果。完整测量方法、英文记录和限制见 [PERFORMANCE.md](PERFORMANCE.md)。

这里的“借鉴”不是直接移植 llama.cpp 的 IQ2 kernel，也不是相同模型在两个运行时之间的性能比较。我们尚未建立同 checkpoint、同权重量化、同输入和同计时定义的 llama.cpp/ORT 对照，因此不能据此判断哪个运行时更快。

## 1. 比较对象和状态

- llama.cpp 源码检查固定在 `c479922ac520a08969b4c1dc154d7bbb3c386d85`，主要关注 CUDA MMVQ、Q8_1 激活量化和 IQ2 点积。较大矩阵使用的 MMQ 是另一条路径，不能将 MMVQ 的结论直接套用到 prefill。
- ORT 实验分支基于 `main@98468bff47`，实验修改仍在本地、未提交为 ORT PR。基准使用匹配构建的 CUDA provider 和 Python binding；基准提交号本身不足以复现实验修改。
- 模型为 Qwen3-30B-A3B，48 层、128 个专家、top-k 8，hidden=2048、intermediate=768。Mixed recipe 只有 24 层的 gate/up 使用 INT2，down 和其余专家投影使用 INT4。
- 实验在 Docker `jiafa-dev`、A100-SXM4-80GB、CUDA 12.8、SM80 上进行。所有实验开关默认关闭，不是本 recipe 已交付的运行时功能，也没有启用生产默认路径。

## 2. 同样叫“2 bit”，不代表相同格式

| 项目 | llama.cpp 的相关实现 | 我们的 INT2 QMoE |
|---|---|---|
| 权重含义 | IQ2_XXS/XS/S 使用码本索引、符号和格式特定 scale，Q2_K 又是另一种格式 | 均匀对称整数值 `[-2, -1, 0, 1]`，已有 GPU packed 布局以 `code - 2` 解码 |
| 权重布局 | GGML 格式专用 block 和对应点积实现 | 为 ORT kernel 预处理的 pair-interleaved 布局，不能直接当作 IQ2 读取 |
| 默认激活计算 | 所检查的量化 MMVQ 路径先生成 Q8_1，再与低比特权重做整数点积 | 基线保持 FP16 激活，在 kernel 内局部解码权重并做浮点点积；INT2 使用 FP32 累加 |
| 激活分组 | Q8_1 每组 32 个值，具有格式定义的 scale/求和元数据 | 原型每组 16 个值，存储 INT8 值和一个 FP32 scale；不是 Q8_1 |
| 解码到整数点积 | IQ2 从码本取值、恢复符号，构成四字节操作数后使用 DP4A | 原型通过字节排列、移位、掩码和减 2，直接构成四个有符号 INT8 值 |
| 激活临时存储 | MMVQ 使用内存池临时缓冲和单独量化 kernel | 预量化原型使用 ORT stream-aware scratch 和单独量化 kernel |
| MoE 索引/复用 | indexed MMVQ 使用专家索引；符合条件时有 up/gate GLU 和 shared-expert 融合 | 保留 QMoE routing，源行映射供多个专家读取；FC1 融合 gate/up GEMV 和 SwiGLU |

IQ2 的标称位宽还不能直接视为每个权重恰好占两位。例如 IQ2_XXS/XS/S 每 256 个权重的 block 分别为 66/74/82 字节，即约 2.0625/2.3125/2.5625 bit/weight，包含元数据。ORT 的“两位 payload”也不包含额外 scale 的存储成本。格式比较需要同时考虑元数据、量化误差和布局，而不只是名称。

源码依据为该 llama.cpp revision 的 [`mmvq.cu`](https://github.com/ggml-org/llama.cpp/blob/c479922ac520a08969b4c1dc154d7bbb3c386d85/ggml/src/ggml-cuda/mmvq.cu)、[`vecdotq.cuh`](https://github.com/ggml-org/llama.cpp/blob/c479922ac520a08969b4c1dc154d7bbb3c386d85/ggml/src/ggml-cuda/vecdotq.cuh) 和 [`ggml-common.h`](https://github.com/ggml-org/llama.cpp/blob/c479922ac520a08969b4c1dc154d7bbb3c386d85/ggml/src/ggml-common.h)。本实验没有验证将激活量化融合进上游 producer 的实现，不能将它写成 llama.cpp 已有能力。

## 3. 我们具体借鉴了什么

思路是让低比特权重在局部整数域中参与点积，而不是先转成浮点再计算；同时把激活量化从每个 dot tile 的重复工作，改为每个原始输入行只做一次，并复用于输出列和选中专家。

基线的数据流是：

```text
packed INT2 weight -> 局部解码和 weight scale -> FP16 操作数
FP16 activation -> 浮点点积 -> FP32 累加 -> SwiGLU
```

预量化原型的数据流是：

```text
FP16 source row -> 16 值一组量化 -> INT8 临时缓冲 + FP32 scale
packed INT2 weight -> 局部整数解码和排列 -> 四字节 DP4A 操作数
INT8 activation + 整数 weight -> INT32 点积 -> 恢复 scale -> FP32 累加 -> SwiGLU
```

激活 scale 为 `amax/127`，量化使用 round-to-nearest 并限制到 `[-127, 127]`。这会新增激活量化误差，不能当作与 FP16 基线数学等价的重排。权重始终以 packed INT2 保留在显存中；没有物化整块 FP16 或 INT8 专家权重。

这也是一个容易混淆的地方：**基线本来就没有先生成整块浮点权重矩阵。** 原型省掉的是局部 INT2→FP16→整数转换，不是省掉一份原本存在的巨大反量化缓冲。

## 4. 实验结果：从局部改写到真实模型

### 4.1 直接整数解码比浮点绕行快，但仍慢于 FP16 基线

最初原型在线量化线程自己的 16 值 activation tile。先让现有 converter 输出 FP16 weight，再转成整数做 DP4A；随后改为直接整数解码。

下表是独立、非融合 GEMV，八个专家使用八个源行，CUDA event 计时。单位为微秒，不是模型 TPS。

| N / K / block | INT2 + FP16 基线 | 浮点解码后转整数 | 直接整数解码 |
|---|---:|---:|---:|
| 1536 / 2048 / 64 | 15.2474 | 29.4349 | 23.5264 |
| 1536 / 2048 / 128 | 15.1245 | 29.2198 | 23.4138 |
| 2048 / 768 / 64 | 9.84576 | 19.5277 | 14.2490 |

直接整数解码使原型比浮点绕行快约 20%–27%，但仍需基线约 1.45–1.55 倍的时间。消除中间转换是有效改进，不等于整条 INT8 路径已更快。初始实验的 INT8 输出相对 FP16 基线 L2 差异约 2.20%–2.54%；这是输出差异，不是任务准确率下降百分比。

### 4.2 预量化复用和直接字节打包

后续原型单独量化原始 source row，再跨输出列和专家复用。权重侧使用 `__byte_perm`、移位/掩码和 `__vsub4`，直接构造 DP4A 操作数，减少中间解码、重排和打包。这里仍然有局部整数解码，不是直接对两位 packed 数据执行 DP4A。

下表采用同一源行被八个专家复用的 CUDA Graph 计时，取三轮中位数。它与前表的源行安排和计时方式不同，不能跨表直接算改写收益。单位为微秒。

| N / K / block | FP16 基线 | 在线 INT8 改写前 / 后 | 预量化 GEMV 前 / 后 | 含量化的总成本前 / 后 |
|---|---:|---:|---:|---:|
| 1536 / 2048 / 64 | 10.8851 | 17.6794 / 12.0269 | 16.0358 / 10.3782 | 18.9235 / 13.1942 |
| 1536 / 2048 / 128 | 10.7571 | 17.5872 / 12.0115 | 16.0102 / 10.3475 | 18.9235 / 13.2762 |
| 2048 / 768 / 64 | 6.55872 | 10.2451 / 7.49568 | 9.40032 / 6.70208 | 12.0166 / 9.31328 |

字节并行打包降低在线 INT8 耗时约 27%–32%，降低预量化 GEMV-only 耗时约 29%–35%。但含量化的总成本仍高于三个对应的 FP16 基线。不能只选 GEMV-only 列来声称端到端提速。

编译报告显示普通 no-bias kernel 的寄存器数：在线版本 96→79，预量化版本 96→56；前后 stack/local storage 都为零，因此不能说消除了 spill。独立量化 CPU 参考、输入映射、零输入、Graph 输出和 memcheck 检查通过。Nsight Compute 硬件计数器采集因 `ERR_NVGPUCTRPERM` 失败，不能据此确认带宽、occupancy 或 stall 的主因。

### 4.3 接入真实 FC1 后，只观察到小幅模型收益

继续优化 activation 的 32-bit 加载、scale 计算和线程配置，并接入 packed INT2 FC1：每个源行量化一次，再执行 gate/up + SwiGLU 融合 kernel，FC2 和 finalize 保持不变。此时实现已不止是上一张表的字节打包版本。

在 GPU 6、同一新运行时和 mixed 模型下，输入 128、输出 16，正反顺序各五次测量、每组两次预热：

| 比较 | 默认 mixed，FP16 激活 | 预量化融合 FC1 |
|---|---:|---:|
| 合并 decode TPS | 111.3843 | 112.8682 |
| 变化 | 基线 | +1.33% |

第二轮 ORT 单步耗时中位数没有改善，不能认定稳健的普遍提速。20 次请求生成的 16 个 token 一致，但没有完整任务准确率评估。独立 Nsight Systems capture 确认 15 个 decode step 中有 360 次量化和 360 次新 INT2 FC1 调用，即每步 24 层；profile 中量化约 3.52 微秒、融合 FC1 约 10.89 微秒。profile 耗时只说明分派和开销，不用于计算模型 TPS。

### 4.4 保留 FP16 激活的 CTA8 对照

另一条路线不量化激活，只将融合 FC1 每个 CTA 的列 tile 从默认 CTA4 改为 CTA8。它不是 llama.cpp 整数点积的移植，也不包含额外量化 kernel。

目标共享输入形状 N=1536/K=2048 的 kernel 延迟在 block64/128 上降低约 16.4%/16.9%，测试输出逐字节一致；K=768 形状却变慢，所以不能全局替换。此前误把默认 INT2 当成 CTA8、再加 CTA4 开关的测试是无效对照，不纳入结果。

GPU 7 上同运行时模型对照如下；两个 INT8 激活开关均关闭，每种配置按正反顺序测量，每个路径十次请求：

| 输入 / 输出 token | 默认 CTA4 TPS | CTA8 TPS | 变化 |
|---|---:|---:|---:|
| 128 / 16 | 111.0333 | 113.6529 | +2.36% |
| 128 / 128 | 110.5721 | 112.7280 | +1.95% |
| 512 / 128 | 108.4455 | 110.0642 | +1.49% |
| 2048 / 128 | 98.7603 | 99.1122 | +0.36% |

2048 输入反向一轮发生退化，不能确认稳定收益。各配置内 token 一致不等于完整准确率验证。这张表与 GPU 6 上的 INT8 原型不是受控的直接对照，不能仅按百分比断言 CTA8 一定优于 INT8。

测量后源码将 CTA8 限制为 SM80、单源行、八个展开专家行、K=2048、inter=768、FP16 无 bias、block64/128。收紧版本的正式对象编译、harness 输出和 fallback trace 通过；block128 只有独立测试证据。上述模型计时来自收紧前的 opt-in 版本，最终收紧运行时的模型冒烟检查尚未记录为通过。没有因此开启默认路径或提交 ORT 优化 PR。

## 5. 为什么“少了 unpack”仍然会变慢？

### 5.1 不是没有解码，而是换了操作数构造方式

DP4A 接收两个各含四个有符号 8-bit 值的 32-bit 操作数，不接受四个或十六个原始两位 code。ORT 仍需恢复符号值并按现有 interleaved 布局聚合字节；llama.cpp 的 IQ2 同样需要码本查询和符号恢复。

因此可以说“避免中间浮点 weight 转换”，不能说“完全不 unpack”。字节打包减少一部分指令，但还保留索引、移位、排列、scale 和累加工作。

### 5.2 省下的工作可能小于新增激活量化成本

在线量化需要求 amax、计算倒数、舍入、截断和打包；相同源 activation 可能在不同列/专家的 tile 中反复量化。预量化消除了这些重复，但引入一个 kernel launch、临时 INT8/scale 写入，以及 GEMV 对临时数据的读取。MMVQ 使用内存池并不意味着没有这些成本；我们的 scratch 管理也不能自动消掉 launch。

前表中 GEMV-only 比基线略快、加上量化却更慢，是这一点的直接测量证据。真实 decode 每步 24 个 INT2 FC1 对应的额外量化 launch 也已由 trace 确认；但具体主机分派、分配和设备访问各占多少，仍需单独测量。

### 5.3 “整数点积”不等于获得 Tensor Core 加速

A100 上本实验使用的是四路 INT8 DP4A 加 INT32 累加，不是原生 packed INT2×INT8 Tensor Core 运算。不能把 Tensor Core GEMM 的吞吐假设套用到小矩阵 GEMV。

此外，FP16 基线已经在 kernel 内局部反量化、保留压缩显存读取，并且复用 activation tile。两边读的权重 payload 都是 INT2；去掉局部浮点转换并不会再次把权重流量减少四倍或八倍。究竟受算术、带宽还是延迟限制，不能只由位宽或指令名称推断。

### 5.4 分组 scale、数据布局和并行度也有代价

我们的 16 值 activation 分组与 Q8_1 的 32 值分组不同，需要更频繁地恢复 activation scale。weight block64/128 又有自身的分组边界，整数部分和浮点 scale 的累加必须协调。scale 外提能减少运算，但会改变浮点结合顺序，并非免费或必然逐位等价。

布局若不适合 DP4A，需要局部排列；寄存器、归约、CTA 数量和缓存复用会随 tile 改变。寄存器数减少是事实，但没有硬件计数器证据证明其为主要瓶颈。CTA8 在 K=2048 更快、K=768 更慢，也说明配置取舍依赖形状，而不是更大 tile 必然更好。

### 5.5 单个 FC1 的改善不会等比例变成模型 TPS

只有 24/48 层的 gate/up 为 INT2，attention、FC2、routing、KV 处理、其他层和主机 orchestration 都不被这项改写消除。若优化部分占总延迟比例为 $f$，其加速比为 $s$，整体理想加速上限是 $1 / ((1-f) + f/s)$；新增量化成本还会进一步抵消收益。

这解释了为什么目标 kernel 约 16% 的延迟降低只对应短上下文约 1%–2% 的模型 TPS 变化。随着上下文增长，其他工作占比可能改变，但现有实验不能把 2048 输入收益减弱严格归因于某一个 attention/KV 瓶颈。共享主机波动和统计样本也需考虑。

## 6. 结论和下一步判断标准

可以借鉴 llama.cpp 的激活预量化复用、格式专用整数解码和符合条件的 GLU 融合，但不能忽略双方格式、分组、调度和运行时边界的差异。少做浮点转换，只证明局部优化方向有效；必须把激活量化、临时读写、launch、scale 和模型其余工作一起计入。

现阶段结论是：直接整数解码优于原型的浮点绕行；预量化复用后真实 FC1 观察到小幅收益；FP16 CTA8 在特定短上下文有收益，但长上下文未证明稳定改善。没有相同模型的 llama.cpp/ORT 性能胜负结论，也没有 INT8 激活路径的完整准确率结论。

是否值得提交 ORT 性能 PR，应以独立可重复的模型收益、目标形状正确性、回退无退化和可维护的分派为标准，而不是以“实现更像 llama.cpp”为标准。本 recipe PR 记录实验和限制，不交付这些本地原型；默认路径保持不变。
